# Server SDK

Server factory:

```ts
export default function plugin(zcc) {
  zcc.log.info(`${zcc.pluginId} loaded`);
}
```

`zcc` is `ZccPluginApi`. Use `zcc.pluginId`, `zcc.log`, `zcc.settings`, `zcc.storage`, `zcc.http`, `zcc.rpc`, `zcc.realtime`, `zcc.background`, `zcc.cli`, `zcc.agents`, `zcc.events`, `zcc.hooks`, `zcc.ui`, `zcc.status`, `zcc.sdk`, `zcc.host`, `zcc.services`, and `zcc.onDispose`.

Settings descriptors use `type: "string"`, `type: "boolean"`, `type: "number"`, `type: "select"`, or `type: "project"`. `zcc.storage.kv` supplies `get`, `set`, `delete`, and `list`; `storage.database()` is per-plugin SQLite. `zcc.http.route` serves under `/api/v1/plugins/<id>/http<path>`. `zcc.rpc.method` and `rpc.register` expose renderer RPC. `zcc.background.service` and `schedule` run durable work. `zcc.cli.register` requires `name` matching `^[a-z0-9-]+$`; core `zcc` names win and output overflow raises `plugin_cli_output_too_large`.

`zcc.agents.contributeInstructions`, `contributeSkills`, `registerTool`, `experimental_registerProvider`, `experimental_registerPtyHarness`, and `configure` shape agent sessions. CLI Agent/PTy sessions need `zcc.mcpServers`, not conversation-only tools. Thread events are `"thread.created"`, `"thread.active"`, `"thread.idle"`, `"thread.failed"`, `"thread.archived"`, and `"thread.deleted"`; payload exposes `name`, `threadId`, `projectId`, `thread`, `lastAssistantText`, and `error`.

`zcc.ui.requestInput({ threadId, rendererId, title, payload, timeoutMs? })` requires a `pendingInteraction` slot whose `id` equals `rendererId`. `zcc.ui.registerMentionProvider({ id, label, triggers?, search, resolve })` supplies `@` / `#` typeahead; never trust renderer-provided context. Approval consumption remains server-side.

Use `zcc.sdk.threads.spawn({ projectId, prompt, providerId?, harness?, parentThreadId?, title?, model?, reasoningLevel?, serviceTier?, permissionMode?, visibility?, hostId?, environment?, pluginMetadata? })`, plus `output`, `stop`, `archive`, `fork`, `unarchive`, `getPluginMetadata`, and `updatePluginMetadata` for thread work. Use `visibility: "hidden"` for workers. `harness: "project-default"` applies project's effective AI harness and rejects when none is usable; explicit `model` and `permissionMode` win. Metadata is namespaced, atomically patched, capped at 256 KiB UTF-8 JSON, and omitted from ordinary thread GET. Use `zcc.sdk.files.read/write` only through host-confined workspace roots. `zcc.sdk.projects.list/setIcon`, `sdk.system.defaultHost`, `sdk.environments`, `sdk.providers.models`, and `sdk.inbox.push` retain host authorization.

For a conversation created by this plugin, `zcc.sdk.threads.interactions.list({ threadId })` lists pending/resolving requests as safe projections: `id`, `threadId`, `kind`, `subjectKind`, `summary`, `summaryTruncated`, `tool`, `allowedDecisions`, `grantPermissions`, `status`, `createdAt`, `resolvedAt`, `resolution`, and `refusalReason`. Summary text is secret-redacted and capped at 1024 UTF-8 bytes (tool names at 256); treat it as untrusted display text and escape it for the external service. Raw tool arguments, plugin data, provider routing ids and plan bodies are omitted. `grantPermissions` is the exact requested profile for a permission grant or command/file session grant.

`zcc.sdk.threads.interactions.resolve({ threadId, interactionId, resolution, actor })` returns the authoritative projection. `resolution` is `{ decision: 'deny' }` or `{ decision: 'allow_once' | 'allow_for_session', grantedPermissions }`. Use `grantPermissions` for permission-grant allows and command/file session allows; use `null` for other allows. The host validates available decisions and exact permissions. Equal retries while resolving/resolved return the current record, without delivering again or overwriting the original actor; different decisions or interrupted requests conflict.

Pass `actor: { kind: 'plugin-relayed-human', pluginId: zcc.pluginId, externalUser: 'tenant/user-id' }`. The plugin must verify the external service signature, authenticate/authorize the external account and bind the human's click to this thread, interaction and decision before calling resolve. `externalUser` must be a stable nonblank account id (at most 256 characters; no control characters). The host captures the calling plugin identity, checks stored `originPluginId`, rejects mismatching actor ids, and records actor plus accepted resolution in a durable `system/operation` timeline event (`operation: 'interaction_resolution'`). Caller metadata alone never grants thread control: pre-existing user threads and other plugins' threads are refused. This relay identity never becomes native `actor: 'human'` or window/sheet attestation. HTTP alone never establishes human authority, and this API neither issues nor consumes native proofs. Human-required plugin forms (`requireHuman: true` or `'native-sheet'`) return `native_confirmation_required`; other forms/questions/custom requests return `unsupported_interaction` and remain pending.

Detect support per thread with `(await zcc.sdk.capabilities.forThread({ threadId })).capabilities.some(c => c.id === 'thread-interactions' && c.available)` and check `zcc.sdk.threads.interactions` exists on older hosts. The descriptor is independent of `interactions` (plugin-owned UI interactions), does not depend on whether an approval is currently pending, and is false without host wiring, for unowned/unknown threads, PTY sessions, or execution-wide queries. Expected failures throw `PluginThreadInteractionError` with `code` (`invalid_request`, `not_found`, `forbidden`, `conflict`, `native_confirmation_required`, `unsupported_interaction`, `unavailable`) and HTTP-style `status`; match `name`/`code` across plugin workers instead of `instanceof`. Host delivery failures propagate; re-list authoritative state before acting again.

`zcc.services.provide/use/has` is live plugin-to-plugin API. Declare `zcc.requires` and import types from provider SDK; do not import provider internals or expose tokens. `zcc.host.experimental_call` and `experimental_client` require configured host entry. Register `zcc.onDispose` cleanup.

`zcc.hooks.on(handler)` is the one message-dispatch admission checkpoint; the request names `surface` (`'modern' | 'pty'`), `entry`, `origin`, and a `threadId` or `sessionId`. `zcc.hooks.onToolPolicy(handler)` needs `"toolPolicy": true` beside `zcc.server` and answers `allow`, `deny`, or `ask` (the host shows a human approval; timeout, cancel, no UI, or a non-human answer denies). `zcc.events.on('tool.settled', handler)` observes how native tool calls ended (state, duration, exit code, output size) with the same `invocationId`; add `"toolResults": "preview"` beside `zcc.server` for a redacted 4 KiB `outputPreview`. A PTY with no thread binding reports its session id as `threadId`; check `surface` and `sessionId` before calling `getThread`. `zcc.sdk.capabilities.forThread` reports what each surface really wires; check it rather than assuming parity. Per-session `configure` and `contributeInstructions` also run for PTY launches (`surface: 'pty'`). `ui.requestInput` accepts a PTY session id as `threadId`. `zcc.host.projectCall` routes to the project's machine. Read the Platform hooks section of `docs/extensions-sdk-reference.md` for budgets and limits.
