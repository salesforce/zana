# Shared instance implementation contracts

The implementation plan and acceptance checklist are in
`.zcc/library/plans/shared-zana-multiple-machines-2026-09-28.md`.
The source comparison is in the linked BB audit. Existing independent Connect
servers remain independent; joining a machine must not create another server.

## Identities and credentials

| Identity | Persistent owner | Authority |
| --- | --- | --- |
| Account | Connect database | Owns instance registrations and devices |
| Product instance UUID | `product-instance.json` in the product data directory | One database and associated product stores, stable across restarts |
| Connect server ID | Existing `connect_servers` row | Address and server tunnel, bound once to a product instance |
| Execution machine ID | `connect_machines` | One account, server and host; distinct from existing phone devices |
| Host ID/key | Product `hosts` and isolated daemon `auth.json` | Enrolled execution runtime; inner authorization remains mandatory |
| Daemon connection instance ID | New random ID for each daemon start | Session/reconnect identity, never the product instance UUID |

Machine grants follow BB's separate machine-pair path. The short-lived inner
enrollment token is encrypted in the cloud using the pairing code; only digests
of machine credentials and retry proofs are stored. The client saves a random
attempt secret before redemption. A retry with that proof returns the same grant
while it is live; another proof cannot consume it. Repair replaces only the
selected host's credential. Neither a phone grant nor a browser cookie grants
host-internal access.

Product join codes are stored as hashes in SQLite with expiry and a bounded
capacity. Only authenticated Connect enrollment may recover a consumed response,
and only while the code, host and instance remain valid. The returned host key is
stable for that private join token and product instance. Ordinary join codes keep
their single-use semantics. Host removal invalidates pending/recovery codes.

## Host purpose and plugin peer links

A product `hosts` row has a purpose: `execution` (the default), or `plugin-link`
with one or more `{pluginId, scope}` uses in `host_link_uses`. Plugin links never
appear in execution listings: `/api/v1/hosts`, Settings → Machines, or a plugin's
`hosts.list`. They are managed only through `/api/v1/peer-links`, the Settings →
Peers hub. Removing one use leaves the link up while another use remains. The
last use tears down the host and revokes its Connect machine. A plugin's
`peers.list` sees only the links it uses. Each link is labelled by its owning
plugin's registered name.

Peer links require **no Connect changes**. Each direction is a base
`connect_machines` row created from a forward-only machine code
(`enrollment_capability = 'peer.forward'`, named `Zana peer link: …`).
Invitation token v2 (`zccinv1.`) carries only
`link: {code, accountUrl, serverId, hostId}`, with no server locator. It expires
at the earlier of 10 minutes and the Connect code expiry. The redeemer:

1. Checks that the token's `accountUrl` is its own.
2. Redeems the code with a saved attempt secret.
3. Confirms through `GET /api/connect/servers` that the redeemed instance is on
   the same account.
4. Enrolls forward-only over the machine route.

Bootstrap then mints the reverse direction the same way. Once both owners
approve, the inviter sends `bootstrap.nudge` over the redeemer's link, so the
redeemer polls right away. Otherwise it would wait for its five-minute status
poll. Only one invitation
link may exist per app pair; another is refused with `already_redeemed`.
Reconnect rotates the link: the destination re-mints the code for its inbound
host, and the peer redeems it, replacing the credential hash in place. A rotation (including the
inviter's first one, which renames its placeholder host) re-keys the link, so every plugin grant bound to
the old key is revoked. A later `peers.enable` for the same scope replaces the superseded binding at once.
Plugins must re-enable after a re-key; Design Docs' initiator does this for the bootstrap scope during setup
and for the database scope after the group forms. Introductions use the
same `{connect}` offer. Base Connect does not check the redeemer's account at
redeem time. The same-account check runs on the redeemer. The inviter opens
sync only after its owner approves the pairing, so paste an invitation only on
the intended computer.

## Machine transport inventory

Both ends of the Connect tunnel use `services/mobile-relay/machine-routes.mjs`.
The website copy is generated by `website/scripts/sync-mobile-relay.mjs`.

| Method | Route | Additional product check |
| --- | --- | --- |
| POST | `/internal/hosts/enroll` | Short-lived join token, instance and reserved host binding |
| WS GET | `/internal/hosts/ws` | Host key, matching hello identity and protocol version |
| POST | `/internal/hosts/tool-call` | Host key and thread ownership |
| POST | `/internal/hosts/interactive-request` | Host key and thread ownership |
| POST | `/internal/hosts/interactive-request/interrupt` | Host key and ownership of affected threads |
| GET/HEAD | `/internal/plugins/:id/host/:digest` | Host key, authorized artifact and bounded payload |
| GET/HEAD | `/install.sh`, `/install/version`, `/install/zcc-host.tgz` | Execution grant; fixed installation artifact routes |

Machine grants cannot invoke owner product APIs or create additional grants.
The edge discards caller-supplied trusted host/instance metadata, checks the
execution credential and stamps the actual identity. The tunnel adds a private
loopback capability. The local gateway checks that capability and its configured
instance before passing through inner host authorization. Browser requests retain
the existing narrow product proxy. Redirects must not leak daemon credentials.
Grant revalidation applies to active streams as well as new requests.

## Product authority inventory

The captured baseline inventory is under
`.zcc/artifacts/shared-machines-implementation/product-authority-inventory.json`
and `direct-desktop-callers.txt`. This is a mechanical family/call-site inventory;
an HTTP family being present is not proof that every method is implemented.

Shared families include projects, configuration, inbox, suggestions, follow-ups,
saved records, goals, schedules, personas, teams, agents, terminals, threads,
environments, execution records, Library and plugin state. Host-local families
include provider logins, repositories, Git, files, local tools and provider
configuration; the selected instance authorizes their selected host/source.
Clipboard, native windows, OS dialogs and client installation updates are local
capabilities. Remote access administration belongs to the authoritative desktop,
while selecting which instance a client displays belongs to that client.

Current `product-client.ts` chooses the preload bridge for many product families.
A remote target must never expose that local product bridge. Merely setting a
different renderer URL does not meet the contract. Test all direct callers and
capabilities with a seeded local canary dataset before enabling desktop targeting.
Keep absent APIs as explicit implementation gaps; do not report browser fallbacks
as complete parity.

## Store ownership and migration

The server owns `zcc.sqlite`, `projects.json`, `config.json`, inbox/suggestion logs
and saved records. Several project families (Library, goals, schedules, follow-ups
and plugin data) still derive paths from the project record. Keep one canonical
metadata locator independent of the execution source. Source files, instructions,
provider secrets and running processes remain host-specific. Do not copy them as
shared settings.

New schemas are additive. Existing IDs, aliases and independent local datasets
stay intact. The migration must not pretend that SQLite transactions cover JSON
or filesystem writes. A shared-project source resolver is required before lifting
the current cross-host project launch refusal. Secondary clients must not start
another scheduler or watcher that writes to the same product records.

## Evidence tracking

The initial cloud enrollment tests passed 29 checks. The first transport regression
run passed 141 checks with optional Postgres/Docker checks skipped. The new
`connect-host-transport.integration.test.ts` passes a real two-host tunnel test:
one product server, two host connections, inner enrollment recovery, tool callback,
wrong-host key denial, browser/phone denial and independent grant revocation.
Its local front door substitutes DNS/TLS, and its command runtimes are fixtures;
this is not the built-Electron or two-physical-machine release gate.

Logs and preserved pre-existing edits are in
`.zcc/artifacts/shared-machines-implementation/`. Do not call the full plan complete
from these foundation checks; retain the plan's acceptance gates through rollout.

## Desktop boundary implementation decision

The first shared desktop surface uses a main-owned, isolated BrowserWindow with
no preload, no Node integration, no webviews and a separate persistent account
session. It uses the same product HTTP/WebSocket surface as browser clients.
This replaces the proposed local-renderer proxy fixture: reusing the remote
browser document prevents the existing direct `window.cc` callers from ever
reaching this client's local product services. Account ownership and target
selection remain in main; the renderer submits a server ID, never a URL.
The selected server/instance IDs persist, URLs are re-resolved from the account
on restore, and unavailable access shows a shared-only error document.
The existing local desktop continues to supervise its independent local work.

Shared-account sign-in opens the system browser. Main starts a bounded desktop
approval request, keeps its private polling secret out of the renderer and URL,
then installs the returned HttpOnly account cookie in the isolated shared
partition. The Connect website serves `/api/connect/desktop/{start,info,approve,poll}`
and preserves `?desktop=` through GitHub OAuth. Deploy that website support before
shipping the desktop change. Approval requests expire after nine minutes, leaving
one minute below released desktops' strict ten-minute ceiling for clock skew.
New desktops tolerate up to one minute of clock skew while capping polling at
ten local minutes. Session expiry has the same one-minute server headroom. Requests require explicit
browser approval, and redeem once; sign-out drains pending cookie writes before
clearing the partition. The picker refreshes automatically after approval.

This decision does **not** establish API parity. Browser API gaps in the inventory
remain qualification work; the shared desktop must not claim unsupported desktop
capabilities or acquire the local full preload. Native conveniences will require
separate, narrow brokered capabilities.

## Project sources storage decision

Extra sources are an additive `sources` array inside the existing serialized,
CAS-protected `projects.json` record. The original `path`/`hostId` remains the
canonical metadata location. This avoids a new cross-store migration and retains
all project IDs, legacy fields and historical environment paths. An execution
projection selects the source for a host without changing the stored project.
New worktrees resolve the execution host's data directory before provisioning.
