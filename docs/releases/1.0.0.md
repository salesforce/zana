# Release notes — 1.0.0

_Baseline: v0.9.0 (2026-07-04). The 1.0 milestone: the app graduates from
"working tool" to a coherent 1.0 surface — the last core→extension seam is
closed (Tickets is now a disk extension), and three new ways to stay on top of
your fleet land: a per-project **Activity Feed**, a macOS **menu-bar popover**,
and **`inbox_ask`** (agents ask you structured questions and block for the
answer)._

A release about **closing the loop and cleaning the seams**. The zana→core
merge that landed the Tickets UI in core is fully reversed — Tickets is a
project-tab disk extension again, and core is provably free of any `'zana'`
literal (Rule 6 is now absolute in the renderer). On top of that: a hybrid
Activity Feed per project, a styled menu-bar fleet popover, interactive
`inbox_ask` questions, launcher **Advanced mode** (persona + framework presets),
**spawn-an-agent** on any follow-up, and the Library grows **full-text search**
plus a batch of security/correctness hardening flagged by the 1.0 review.

> Some of this shipped as commits since v0.9.0; the zana-tickets re-extraction,
> Activity Feed, menu-bar popover, and `inbox_ask` work is staged in the working
> tree at the time of writing. The entries below describe the 1.0.0 surface as a
> whole.

---

## Highlights

### Tickets is a disk extension again (`zana-tickets`)
The renderer surface that the zana→core merge folded into core has been
**extracted back out** into the `zana-tickets` disk extension. This closes the
last core↔extension seam and makes core provably framework-agnostic.

- The UI (`ProjectTicketsView`, `TicketDetailModal`, `VersionSettings`,
  `ticketsStore`, `ticketsApi`, `zanaPrefs`, `ticketColumns`) now lives in
  `plugins/zana/renderer/*`; the extension shell (manifest, react/jsx shims,
  `renderer-entry.tsx`, pack scripts) is `extensions/zana-tickets/`.
- It's a **project-tab-only** contribution (`projectTab.global: false`) — no
  top-level sidebar entry — scoped to `host.getActiveProject()`.
- The **`zana` main module stays a core built-in** (native better-sqlite3 can't
  cross the extension `utilityProcess` boundary); the extension owns only the
  renderer and reaches the trusted in-process provider through the generic
  module bus (`window.cc.modules.call('zana', capability, [arg])`) via its own
  `ticketsApi` data seam — main re-authorizes every source path (Rule 1).
- **Core is now fully zana-free**: no Overview KPI line, no `zana-status`
  palette command, no `SettingsPanel` version section (the `@zana-ai/mcp`
  version check moved into the extension's own `settingsPanel`). The Rule-6
  source-text guard now fails on **any** bare `'zana'`/`"zana"` token anywhere
  in `src/renderer/**`.
- The extension bundles no CSS — it styles via core's shared `gus-*`/`zana-*`
  classes; those class defs must not be deleted as "unused." See
  [`docs/zana-core-merge.md`](../zana-core-merge.md) for the full merge +
  re-extraction migration and rollback notes.

### Activity Feed — a per-project milestone timeline
A new per-project **Activity Feed** tab renders a newest-first timeline of the
milestones that actually matter: git commits, inbox reports, resolved
follow-ups, completed goals, library docs, and extension/project lifecycle
events — with an AI **recap** card at the top.

- **Hybrid model** (design council: `.zcc/library/designs/project-activity-feed.md`):
  most events are DERIVED live from the stores that already persist them
  (inbox / followups / goals / library), so nothing is duplicated; only the
  greenfield events with no other home (git commits, ext + project lifecycle)
  are persisted in `FeedStore`. Only MILESTONE/OUTCOME events make the cut — not
  raw agent-status flips or per-session spawns.
- **Feed recap** mirrors the Inbox AI Summary: main assembles the feed from its
  own `FeedService` (source of truth, never a renderer list — Rule 1), renders a
  compact digest, and runs the `builtin:feed-digest` micro-call into
  `{ headline, highlights[] }`. Capped at the newest `FEED_SUMMARY_MAX_EVENTS`
  (60); never throws.
- Files: `src/main/feed-service.ts`, `feed-store.ts`, `feed-summary.ts`,
  `src/renderer/components/ProjectFeedView.tsx`, `src/renderer/util/feedGrouping.ts`.

### Menu-bar popover (macOS) — a styled fleet snapshot
A frameless-card menu-bar popover replaces the native tray context menu on
macOS: a live, read-only view of the fleet (agents, their state, scheduler)
anchored under the tray icon, hidden on blur.

- Every snapshot is built in **main** from the pty + agent-state + scheduler
  singletons the window already reads; every action routes back through a
  main-authorized handler (Rule 1). Data subscriptions are wired once at app
  init and torn down on `stop()` (Rule 3).
- macOS-only, gated behind `menubarPopoverEnabled` + the darwin check; other
  platforms keep the native menu. Design:
  `.zcc/library/designs/menubar-popover.md`.
- Files: `src/main/menubar.ts`, `src/renderer/components/MenubarPopover.tsx`.

### `inbox_ask` — agents ask you a structured question and wait
The interactive sibling of `inbox_push`. Instead of a plain markdown message,
an agent can pose a **multiple-choice question** (lettered options + optional
free-text "Other…" + Skip/Continue); your choice is injected back into that
session's pty via the same `terminals.reply` channel the ReplyBox uses — so an
agent that asks and then blocks gets your answer "as if typed."

- Identity matches `inbox_push`: `projectId`/`sessionId` come from the MCP URL
  route, never agent-suppliable. **Session-scoped only** — without a live
  session there's nowhere to inject the answer, so it's not registered on the
  project-only route. The host assigns the stable A/B/C letters (an agent can't
  collide two options on one key).
- The question text is stored in the entry's `comments` (so sidebar preview,
  search, AI-summary, and PDF export pick it up for free); options live in the
  entry's `question` field.
- Files: `src/main/inbox-ask-mcp-tool.ts`, `src/renderer/components/InboxSummaryModal.tsx`.

### Launcher Advanced mode — persona + framework presets
The Quick Agent launcher gains an **Advanced** disclosure with two curated,
mutually-exclusive, both-optional pickers:

- **Persona picker** — spawn with any configured persona.
- **Framework presets** — installed extensions may declare an `agentPreset` in
  their manifest (label / description / icon / systemPrompt / initialPrompt /
  model / baseProfile); the launcher surfaces these as selectable chips.
- Picking a framework injects its `systemPrompt` via the **existing** persona
  path: main resolves the `frameworkId` against its own trusted extension
  registry (never a renderer-supplied primer — Rule 1), mints an ephemeral
  host-stamped persona (`framework:<id>`), and routes it through
  `resolvePersonaLaunch → --append-system-prompt`. No per-framework code in core
  and no extension id in launch logic (Rule 6) — the manifest `agentPreset` is
  the sole decoupling seam, same pattern as `projectTab`. Typing a task
  suppresses the preset's `initialPrompt` so the two turns don't collide.

### Spawn an agent to work a follow-up
Every open follow-up gets a **Spawn** affordance (rocket icon in the compact
row, "Spawn agent" button in the detail). It spawns a Claude agent in the
follow-up's **own** project (so its route-scoped `followup_*` MCP tools resolve
correctly), seeds the first turn with full context via `buildFollowUpPrompt`
(title, kind framing, detail body, and an instruction to `followup_resolve` the
record by id when done), and jumps into the new terminal.

- The agent-facing `followup_create` contract is strengthened too: the
  description and `detail` schema now insist on real context (what you were
  doing, findings, options + trade-offs, paths/commands/links, what a good
  answer looks like) so a spawned agent can act without the original session.
- Files: `src/renderer/util/followUpPrompt.ts`, `FollowUpsPanel.tsx`,
  `src/main/followup-mcp-tools.ts`.

### Library — full-text search + 1.0 hardening
The Document Library gained **full-text search of document bodies** (not just
title/summary/tags) via `window.cc.library.search`, plus a batch of
security/correctness fixes surfaced by the four-team 1.0 review
(`.zcc/library/findings/library-review-1.0.0.md`):

- **[CRITICAL]** Agents could hijack/delete *untracked* docs — the
  `agentWrite`/`agentRemove` guard now treats a missing `source` as non-agent
  (a fresh clone reconciles user docs as untracked, so this was cross-machine).
- **[HIGH]** `agentRead` is now size-capped to match the renderer, closing an
  unbounded-read OOM/DoS.
- **[MED]** `reconcile()` no longer follows symlinks out of the tree (realpath
  prefix check), and de-dups manifest entries by relPath.
- **[MED]** Front-matter closing-fence detection fixed so a body starting with a
  `---` horizontal rule round-trips.

## Upgrade notes

- **No data migration.** Existing tickets/sprints continue to work unchanged —
  the `zana` main module (the data provider) was never moved; only the renderer
  UI became an extension, which is reseeded from the app's bundled extensions on
  first launch.
- The **Activity Feed** persists only greenfield events (`FeedStore`); its other
  rows derive live from existing stores, so there's nothing to migrate.
- `inbox_ask` is registered on the session route and pre-approved alongside
  `inbox_push`; existing sessions pick it up on next launch.
- The **menu-bar popover** is macOS-only and gated behind `menubarPopoverEnabled`.
