# Release notes — 0.8.7

_Baseline: v0.8.6 (2026-06-28). This is the first per-release notes file; earlier
releases are captured only as git tags._

A release focused on **closing the inbox loop** (agents can now read it back, and
the user gets an AI digest of it), a new **cross-project Zana Hub** extension, and
**project-focus navigation** that lets the main window drill into one project
without spawning a separate window. Plus the website/hosting work and the
"Orchestrator → Chat" rename.

> Some of this shipped as commits since v0.8.6; the inbox-summary / inbox-search /
> zana-hub / project-focus work is staged in the working tree at the time of
> writing. The entries below describe the 0.8.7 surface as a whole.

---

## Highlights

### Inbox AI Summary
A standup-style digest at the top of the Inbox — a one-line headline plus
"what got done" and "needs your attention" bullets — so you don't have to scan
every entry.

- View-driven and throttled: mounting the inbox triggers a debounced refresh,
  with a hard floor of ~10 min between *automatic* regenerations (a manual
  refresh button bypasses the throttle). The digest is cached per scope and only
  regenerates when the inbox content signature (entry ids + timestamps) changes.
- Runs a cheap `builtin:inbox-summary` micro-call (Haiku), capped at the newest
  60 entries; never throws — failures fall back to a "couldn't summarize" state.
- Scopes to the focused project when you've drilled in, or summarizes the whole
  inbox otherwise.
- Files: `src/main/inbox-summary.ts`, `src/renderer/components/InboxSummaryCard.tsx`,
  `useInboxSummary` in `src/renderer/store.ts`, `builtin:inbox-summary` in
  `src/main/prompt-registry.ts`, IPC `inbox:summarize` + `InboxDigest` /
  `InboxSummaryResult` types.

### `inbox_search` — agents can read the inbox
The read counterpart to `inbox_push`. Agents can now list recent entries or
substring-search the inbox to answer "what's in my inbox?", find an earlier
entry, or check whether they already reported something.

- Read-only; never mutates. Pre-approved by default alongside `inbox_push`.
- **Project-confined by default** — the project identity comes from the MCP URL
  route (CLAUDE.md rule 1), not from the agent, so it can't peek at another
  project. `allProjects: true` is the one explicit, opt-in cross-project read.
- Bounded: scans the newest 500 entries and filters in-process (no index),
  paginates via `before`, returns a projected `{ id, ts, projectId, projectLabel?,
  comments?, docs?, occurrences? }`.
- Files: `src/main/inbox-search-mcp-tool.ts`, registered on both route shapes in
  `src/main/mcp-server.ts`, allow-listed in `src/main/pty.ts`, documented in
  `resources/inbox-skill.md`.

### Zana Hub extension (new) — a cross-project view of the Zana framework
The per-project Zana tab shows one project's tickets/sprints; **Zana Hub** is a
global-only sidebar dashboard over the shared `~/.zana` framework: teams,
profiles, skills, recent runs, workers, and autopilot goals.

- Reads `~/.zana` through the brokered `ctx.fs` (sandboxed to that path), bounded
  at 200 files per directory; a missing dir or corrupt file is skipped with a
  recorded warning rather than failing the whole call.
- Global-only by design: declares **no** `projectTab`, so it's sidebar-only (the
  default) — a cross-project tool with no per-project tab.
- Out of scope (on-disk artifacts only): the SQLite tickets DB and in-flight
  deliberations.
- Lives at `extensions/zana-hub/` with a prebuilt mirror under
  `examples/extensions/zana-hub/`.

### Project-focus navigation
The **main window** can now drill into a single project (a soft focus) instead of
only opening a separate per-project window. Clicking an agent card or a project
row calls `enterProjectFocus(projectId)`; the rail switches to the project-scoped
nav (Inbox · Agents · Terminals · Explorer · Library · Zana · Goals · Follow-ups)
with a **"← Projects" back button** and a slim global footer so a focused project
is never a trap. Focus is persisted across relaunch via
`AppConfig.focusedProjectId`.

- Files: `focusedProjectId` / `enterProjectFocus` / `exitProjectFocus` in
  `src/renderer/store.ts`, the `'focus'` variant of
  `src/renderer/components/ProjectScopedNav.tsx`, routing in
  `src/renderer/App.tsx`.

### Orchestrator → "Chat"
The Orchestrator panel is now labelled **Chat** ("chat with the app itself" — a
single super-agent that operates everything by spawning teams and running
agents), carries an "under development" tag, and got a session-list refresh
(search/filter, "+ New chat", avatar+pill layout). Files:
`src/renderer/components/OrchestratorPanel.tsx`, `src/renderer/styles/global.css`.

## Extensions

- **`projectTab.global` flag.** Extensions can now opt **out** of their top-level
  sidebar entry with `projectTab.global: false` — surfacing only as a per-project
  tab (no cross-project global view). Absent/`true` keeps the default dual
  surface (global sidebar entry **and** per-project tab). Wired through
  `packages/extension-sdk/src/index.ts`, `src/main/extensions/discovery.ts`
  (`parseProjectTab` / `toManifestView`), and `ExtensionManifestView` in
  `src/shared/types.ts`.
- **Consensus** is now project-scoped: it sets `projectTab.global: false`, its
  main `list()` filters by `projectId`, and the panel reads
  `host.getScopedProjectId()` to decide whether to filter.
- **Marketplace is now discoverable and non-empty by default (VSCode-style).**
  Two changes close the gap with an editor's Extensions view:
  - **Top-level "Extensions" rail entry** (`src/renderer/components/ExtensionsPanel.tsx`,
    wired in `Sidebar.tsx` / `App.tsx` / `store.ts` `CoreNavId`) — the browse/install
    front door, opening the hub on its **Marketplace** tab. Settings → Extensions
    stays for versions & per-extension settings; the hub component is shared
    (`ExtensionsHub` gained an `initialTab` prop).
  - **Bundled catalog.** `listMarketplace` now unions the first-party extensions the
    app ships (`listBundledCatalog` in `extension-installer.ts`, read generically from
    the bundled root — no extension id in logic, Rule #6) with the opt-in remote
    registry. A remote release for an id **wins** over its bundled twin. So the
    marketplace shows real, installable extensions with **zero network** by default;
    the remote channel stays strictly opt-in (no host reaches the network unless
    `~/.zcc/extension-registry.json` opts in). Each row carries a `source`
    (`'bundled'` | `'marketplace'`) rendered as a provenance badge.
  - **`{ kind: 'bundled', id }` install source** (`installFromBundled`) reinstalls a
    removed first-party extension from the app's own resources — main maps id → the
    app-owned bundled dir (never a renderer path, Rule #1) and re-runs the same
    manifest/id/api/reserved gates as every install path.

## Website & hosting

- Next.js static-export site (landing, marketplace, docs, download) with a
  docs-sync pipeline and IP-gated hosting (Heroku/Docker). `getting-started.md`
  was retired from the site tree in favour of the canonical README.

## Fixes & housekeeping

- Resolved non-breaking `npm audit` vulnerabilities (#17).
- Auto-dismiss finished agents from the lists after 60s; favorite-star no longer
  overlaps the status dot.
- Terminal: `Shift+Enter` no longer also submits.
- E2E: Playwright + Electron framework, starting with the marketplace.

## Upgrade notes

- No data migration. New on-disk surfaces (`.zcc/followups/`, `.zcc/goals/`,
  `.zcc/library/`) are created lazily.
- `inbox_search` is pre-approved automatically; existing sessions pick it up on
  next launch (the MCP server is re-wired by the launcher).
- The Consensus extension no longer shows a global sidebar entry — its decisions
  live only on the per-project Consensus tab.
